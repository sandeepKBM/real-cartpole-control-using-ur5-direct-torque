## Report-only (safety/hardware-motion-adjacent — do not silently patch)

### 1. `direct_torque` mode opens the real RTDE **control** socket before `motion_opt_in` is checked, in two separate call paths

**Confidence: high (read and confirmed directly).**

`hardware/x_transport.py:129-130`:
```python
link = UR5eDirectTorqueLink(robot_ip, frequency_hz=500.0)
link.connect()
if not skip_joint_move:
    ...
```
`UR5eDirectTorqueLink.connect()` (`hardware/direct_torque_link.py:56-80`) unconditionally opens
both the RTDE receive **and control** interfaces — there is no `with_control` parameter to
defer the control socket, unlike `UR5eLink.connect(with_control=...)`. `motion_opt_in` is only
checked two calls later, inside `move_joints_to_pose()` (`hardware/joint_motion.py:36`) and
`run_x_transport_direct_torque()` (`hardware/direct_torque_transport.py:80-81`) — by which
point the control connection (a real, robot-visible "external control" claim per RTDE
semantics) is already live. Contrast with the `position` branch two lines above it
(`hardware/x_transport.py:104-127`), which checks `motion_opt_in` *before*
`link.connect(with_control=True)` in both `_joint_move_ur5e_link` and
`run_x_transport_position`.

Second, independent instance of the same root cause: `tools/ur5e_direct_torque_x_transport.py`
— `power_on_and_release()` (real dashboard power-on/brake-release commands) runs
unconditionally at the top of `main()` (`:187-192`), before both the `--probe-only`
short-circuit and the `--i-understand-this-moves-the-robot` check (only gated by
`--skip-dashboard-power-on`); the two sibling scripts
(`ur5e_direct_torque_height_latency_test.py`, `ur5e_urscript_x_transport.py`) both check the
opt-in flag first. Worse, `--probe-only --control-mode direct_torque` (`:203-214`) calls
`UR5eDirectTorqueLink.connect()` and then `link.safe_stop("probe_complete")` — a real
`stopJ()` on the robot — **both before** the opt-in check at line 222. A plain
`--probe-only --control-mode direct_torque` invocation with no opt-in flag still takes
control authority and sends a stop command to the physical robot. The sibling `position`-mode
probe and `ur5e_direct_torque_height_latency_test.py`'s `--probe-only` both correctly use
`with_control=False`.

**Currently exploitable?** Not through the two real CLI callers of `run_x_transport`
(`tools/ur5e_direct_torque_x_transport.py`, `tools/ur5e_direct_torque_height_latency_test.py`)
— both gate on `--i-understand-this-moves-the-robot` at argparse level and hardcode
`motion_opt_in=True` at the call site — but `tests/hardware/test_x_transport.py` has no test
exercising `run_x_transport(control_mode="direct_torque", motion_opt_in=False)`, so the gap is
untested, and the `--probe-only` path is a real, exercised-by-design "receive-only, cannot
move" contract that this violates today.

**Fix direction**: give `UR5eDirectTorqueLink.connect()` a `with_control` parameter mirroring
`UR5eLink.connect`; check `motion_opt_in` in `run_x_transport`'s `direct_torque` branch before
calling `connect()` with control, and in `tools/ur5e_direct_torque_x_transport.py`, move the
opt-in check before both `power_on_and_release()` and the probe-only connect.

### 2. The new `wrist_orientation_task` controller flag is silently dropped by the URScript generator — no error, no warning

**Confidence: high (confirmed via grep — zero references anywhere in `urscript_gen.py` or its tests).**

Today's (uncommitted-at-audit-time, since landed as `4b30491`) `wrist_orientation_task` /
`kp_rot_wrist` / `kd_rot_wrist` fields on `CartesianImpedanceConfig`
(`controller_core/x_axis_cartesian_impedance.py`) add a joint-space PD term specifically
built to fix the directional orientation-holding ceiling documented in AGENTS.md §3
(2026-07-27/28 finding). `hardware/urscript_gen.py`'s `load_params_from_yaml()` never reads
these three fields, and `render_urscript()` has no equivalent to the guard it already has for
nonzero `kp_rot` (`urscript_gen.py:128-134`, which explicitly raises rather than "silently
drop the term on the real arm" — the on-robot template has no wrist-orientation-mask PD term
at all). If a config validated in MuJoCo with `wrist_orientation_task: true` is later pointed
at `--control-mode urscript`, the generated script silently omits the correction —
reproducing exactly the failure mode the flag exists to fix, with a summary that looks
identical to a healthy run. This is a fresh instance of the exact class of risk AGENTS.md §4
already documents for Mode 3 ("runs a hand-ported control law, not the validated one").
Currently latent — no named config sets the flag yet.

**Fix direction**: extend `render_urscript()`'s existing `kp_rot` guard to also raise on
`wrist_orientation_task` / nonzero `kp_rot_wrist` / `kd_rot_wrist`, until the template is
extended to implement the term.

### 3. `run_urscript_x_transport` skips the `move_duration_s > duration_s` validation the other two transports enforce

**Confidence: medium (real gap, low severity).**

`hardware/direct_torque_transport.py:120-121` and `hardware/position_transport.py:119-122`
both `raise ValueError` on `move_duration_s > duration_s`. `hardware/urscript_transport.py`
has no equivalent check (its profile logic is baked into the generated URScript instead of
using `x_profile_target`, so the shared Python-side guard doesn't naturally apply). Impact is
low — the on-robot script's `while t < duration_s` loop is itself bounded, so a bad value just
ends the move abruptly via `stopj(2.0)` rather than causing a runaway — but it's an
inconsistent input contract across the three CLI-exposed transport modes.

### 4. `simulation/ur5e_mujoco_torque.py`: `gravity_source: "pinocchio"` is silently a no-op through every real call path

**Confidence: high (live-reproduced by the background audit agent).**

`build_mujoco_state(..., gravity_compensation=True)` (the default, and what every real caller
passes) precomputes `state.gravity_torque` via MuJoCo's native `compute_gravity_torque`,
independent of `gravity_source`. `MujocoUR5eTorqueAdapter._gravity_torque`
(`simulation/ur5e_mujoco_torque.py:428-436`) checks `if state.gravity_torque is not None:`
*before* checking `self.cfg.gravity_source == "pinocchio"`, so the Pinocchio branch is dead
code whenever the precomputed value is present — which is always, in
`tools/ur5e_mujoco_torque_experiments.py`, `rl_gain_scheduling/gain_scheduling_env.py`, and
even the new residual-observer test (`tests/mujoco/test_direct_torque_residual_observer.py`).
Confirmed still present as of `f6241b8` (the concurrent session's own caching commit touched
this same function without fixing the ordering).

**Practical impact is low**: AGENTS.md documents MuJoCo/Pinocchio gravity parity at <1e-8 Nm
for this model, so no run's physics is numerically wrong — but the landed `gravity_source`
P1 feature and its intended fast-path selection have no effect through any production call
path, and any future divergence between the two dynamics sources would silently never be
picked up. Not fixed here: the file was under active concurrent development throughout this
audit, and the correct fix requires a design choice (tag the precomputed value with the
source it was computed with vs. always recompute in `_gravity_torque` when
`gravity_source == "pinocchio"` vs. change `build_mujoco_state` itself) rather than a
single obvious mechanical change.

### 5. `simulation/ur5e_mujoco_torque.py` + `tools/ur5e_mujoco_torque_experiments.py`: `--transport-axis-index 1|2` silently becomes a no-op for the `torque_qp` controller

**Confidence: high (live-reproduced by the background audit agent).**

Both `build_initial_state_and_adapter` (`simulation/ur5e_mujoco_torque.py:734-735`) and the
main per-step loop (`tools/ur5e_mujoco_torque_experiments.py:751`) always build
`target_ee_pos` with the transport delta applied to index 0 (`target_ee_pos[0] = ee_pos[0] +
target_x_delta`), regardless of `transport_axis_index`. `TorqueTaskQPController._desired_pose`
(`controller_core/torque_task_qp.py:130-142`) has a correct axis-aware fallback for exactly
this case, but that fallback is dead: since `target_ee_pos` is always supplied non-`None`,
`_desired_pose` takes the `if target_ee_pos is not None: p_des = target_ee_pos` branch instead.
Combined with the same controller's hold-orthogonal-axes logic (`torque_task_qp.py:183-189`,
which holds every axis except `axis_idx` at the start pose), the net effect with
`--transport-axis-index 1` (or `2`) and `--controller torque_qp` is: the commanded axis (Y or
Z) never receives the delta, and the erroneously-applied X delta is discarded too (X isn't
`axis_idx` either) — the whole move becomes a no-op hold. Reachable today via
`tools/ur5e_mujoco_torque_experiments.py --transport-axis-index 1|2 --controller torque_qp`
(a documented, validated CLI combination); `tests/unit/test_torque_task_qp.py` only exercises
the controller in isolation with a manually-correct `target_ee_pos`, masking the integration
gap. Not fixed here for the same active-concurrent-development reason as finding 4, though
this one is more mechanical (`target_ee_pos[transport_axis_index]` instead of
`target_ee_pos[0]` in both call sites).

## Fixed directly (low-risk, non-safety, stable files — tests added, full suite green)

### 7. `simulation/workspace_guardrails.py`: a single inactive/placeholder boundary permanently poisoned every future "inside" verdict to "unknown"

**Confidence: high (reproduced by the background audit agent; independently confirmed and fixed).**

`_assess_boundary` (`simulation/workspace_guardrails.py:403-414`) correctly returns
`state="unknown"` for any `BoundarySpec(active=False)` placeholder. But `_combine_assessments`
(`:466-519`) OR'd `state == "unknown"` across **every** boundary in the config, not just the
one being queried:
```python
unknown = any(a.state == "unknown" for a in assessments)
...
if unknown: return unknown   # fires for ANY inactive boundary, always
```
So a single `active: false` entry anywhere in `config.boundaries` meant `check_point`/
`check_trajectory` could never return `"inside"` again, for any point, no matter how safely
inside the real active boundaries it was. This module is explicitly simulation/visualization
only per AGENTS.md §2 ("never wire it into real-arm e-stop logic"), so the impact is confined
to sim-side tooling (`tools/diagnostics/render_guardrail_overlay.py`,
`check_trajectory_guardrails.py`). Currently unreached because the shipped
`config/lab_workspace_guardrails.yaml` has zero `active: false` boundaries — the three
genuinely-unresolved boundaries are kept in a separate `unresolved:` list rather than as
inactive `BoundarySpec` entries, sidestepping the bug by accident, not by design (the
dataclass explicitly supports `active`/`unresolved_reason` per-boundary for exactly the
"unresolved placeholder" use case its own docstring describes).

**Fix**: added a `BoundaryAssessment.active` field (mirroring `BoundarySpec.active`, default
`True`, included in `.as_dict()`), set `active=False` on the inactive-boundary assessment, and
changed `_combine_assessments` to only let an *active* boundary's `state == "unknown"` block
an "inside" verdict (`simulation/workspace_guardrails.py:230-256, 403-414, 466-522`).
`check_trajectory`'s per-point aggregation consumes `_combine_assessments`'s already-corrected
decision, so no separate fix was needed there.

**Test**: `tests/unit/test_workspace_guardrails.py::test_inactive_placeholder_boundary_does_not_block_inside_verdict`
— appends an `active=False` placeholder boundary to a deep-copied loaded config, verifies a
point that was `"inside"` before the placeholder still reports `"inside"` after, and that the
placeholder itself is still surfaced in `decision.assessments` with `state="unknown"`,
`active=False`.

### 8. `observability/run_logger.py`: a summary with zero success evidence silently defaulted to `outcome="success"`

**Confidence: medium (real design defect; confirmed currently unreachable through both real callers).**

`build_record_from_summary` (`observability/run_logger.py:380-389`) fell through to
`success = True` whenever a `summary.json` had none of `success`, `termination_reason`, or
`hold_valid_normal` — e.g. a partially-written/crashed summary, or a future driver that
doesn't populate these fields — directly contradicting this module's own stated purpose
("Do not trust an MP4 or a bare exit code as success evidence — read the run record",
AGENTS.md §2) and feeding straight into the logged `outcome`/`failure_category` fields.
Confirmed unreachable today: both real callers (`tools/ur5e_move_hold_transport.py`,
`tools/audit_ur5e_mujoco_gravity_torque.py`) always populate at least one of the three keys,
and `tests/mujoco/test_run_logger.py` had no test for the true zero-evidence case (its
closest test always still sets `hold_valid_normal`).

**Fix**: changed the fallback default from `success = True` to `success = False`
(`observability/run_logger.py:380-395`) — absence of failure evidence is not success evidence.
This is a narrow default-direction change, not a schema change (no new `"unknown"` outcome
category introduced, since that would need a broader design decision about how `outcome`/
`failure_category`/CSV consumers should represent a third state).

**Test**: `tests/mujoco/test_run_logger.py::test_zero_evidence_summary_defaults_to_failure_not_success`
— builds a summary with `success`, `termination_reason`, and `hold_valid_normal` all absent,
asserts `record.outcome == "failure"`.
